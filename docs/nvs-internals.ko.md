# NVS에 상태 저장하기

펌웨어는 타이머로 깨어나 한 번 조회하고 화면을 그린 뒤 다시 딥슬립함. 딥슬립 웨이크는 `setup()`부터
다시 시작하고 일반 RAM은 전부 사라지므로, 마지막 성공 응답을 **매 웨이크마다 저장소에서 다시 읽어야
함**. 그 저장소가 NVS.

아래 수치는 한 기기의 덤프에서 나온 값이고 "이 덤프에선"으로 표시함. 표시가 없는 것은 NVS 포맷이
고정하는 값.

관련: [저장과 화면 갱신](persistence-and-refresh.ko.md).

---

## 1. 왜 RTC 메모리가 아닌가

RTC SRAM은 딥슬립은 버티지만 리셋 버튼·재플래시·전원 차단에서는 지워짐 — 개발 중엔 자주 일어남
NVS는 다 버티는 대신 플래시 erase를 씀(§6). 전체 비교표와 전력 수치는
[저장과 화면 갱신](persistence-and-refresh.ko.md) 참고.

---

## 2. NVS가 무엇인가

**N**on-**V**olatile **S**torage — ESP-IDF가 전용 플래시 파티션에 두는 키-값 저장소.
Arduino에선 `Preferences`로 감싸져 있음.

**EEPROM이 아님.** ESP32엔 EEPROM이 없어서, NVS는 펌웨어가 들어있는 같은 SPI NOR 플래시에 씀.
Arduino의 `EEPROM` 라이브러리도 같은 플래시 위의 더 얇은 에뮬레이션. ESP-IDF는 이 스토리지 계층을
기본 포함해서 배포하고, 그렇지 않은 MCU에서는 웨어 레벨링·페이지 스왑이 애플리케이션 몫이 됨.

---

## 3. API

```cpp
prefs.begin("weather", false);          // 네임스페이스, false = 읽기쓰기
prefs.putString("last", value);
String w = prefs.getString("last", ""); // 두 번째 인자 = 키가 없을 때 기본값
prefs.end();
```

- **네임스페이스와 키는 개발자가 정하는 이름.** 어디에도 선언돼 있지 않고, 첫 `putString()`이 키를
  생성함.
- 이름은 최대 15자, 문자열 값은 최대 4000바이트.

---

## 4. NVS가 플래시에 쓰는 것

![NVS 구조 (한 기기 덤프 기준): 4MB 플래시 → nvs 파티션의 페이지 5개 → ACTIVE 페이지 → 값이 담긴 32바이트 엔트리](nvs-layout.png)

네 개 층이 차례로 안에 중첩돼 있음. **엔트리**는 페이지 안 126개 자리 하나를 뜻하고,
그림에는 `slot`으로 표시돼 있음:

| 단계 | 크기 | 담는 것 |
|---|---|---|
| 플래시 칩 | 4MB *(이 보드)* | 모든 파티션 — 펌웨어, 파일시스템, `nvs` |
| `nvs` 파티션 | 20KB *(파티션 테이블)* | 페이지 5개 *(= 크기 ÷ 4KB)* |
| 페이지 | 4KB *(NVS 포맷)* | 헤더(32B) + 엔트리 상태 비트맵(32B, 엔트리당 2비트) + 엔트리 126개 |
| 엔트리 | 32B *(NVS 포맷)* | 첫 엔트리에 키가 들어가고, 값은 8바이트 이하면 같은 엔트리에, 크면 다음 엔트리들에 |

### 키와 값이 어디에 들어가나

키-값 한 쌍이 차지하는 엔트리들 중 **첫 엔트리**의 32바이트 구성 (뒤따르는 엔트리에는 이런 구조
없이 값 바이트만 들어감):

```
byte  0      NsIndex     네임스페이스 번호 (이름이 아님)
byte  1      Type        0x21 = 문자열, 0x01 = uint8, …
byte  2      Span        이 항목이 차지하는 엔트리 수
byte  3      ChunkIndex  여러 페이지에 나뉜 blob의 조각 번호, 그 외엔 0xFF
bytes 4–7    CRC32
bytes 8–23   Key         16B — 이름 15자 + 널 (이름이 15자로 제한되는 이유)
bytes 24–31  Data        8바이트 이하 값은 여기 통째로, 크면 길이와 CRC32만
```

- **키는 언제나 `Key` 필드에 통째로** 들어감.
- **값이 8바이트 이하면**(`int`·`bool`·`float`) `Data`에 그대로 → **엔트리 하나로 끝.**
- **값이 그보다 크면** `Data`엔 길이와 CRC만 두고, 실제 바이트는 **뒤따르는 엔트리들**로 넘어감.

키 `"last"`에 58바이트 문자열을 저장하면 이렇게 놓임:

![엔트리 목록에서 slot 1의 32바이트 내부로 확대: Ns·Type, CRC32, 16B Key, 8B Data, 그리고 값이 넘쳐간 slot 2·3](nvs-entry.png)

`Key`(16B)가 `Data`(8B)보다 커 보이지만 값에 실제로 쓰인 공간은 64B. **키는 길이가 유한해서 인라인,
값은 무한해서 넘치는 구조.**

값이 길수록 엔트리를 더 씀 — 헤더 1개에 값을 32바이트씩 담을 엔트리가 더해짐. 길이는 글자 수가 아니라
바이트 수라 UTF-8 `ü`는 2바이트로 셈.

### 저장할 때 일어나는 일

1. **새 엔트리를 뒤에 추가.** 네임스페이스 문자열은 맨 처음 한 번만 저장되고 번호를 받으며
   (이 덤프에서 `"weather"`는 `7`), 이후 엔트리는 그 1바이트를 `NsIndex`에 담음.
2. **옛 사본은 표시만 바뀜.** 데이터는 그 자리에 남고, 엔트리 상태 비트맵의 2비트만
   `Written` → `Erased`로.
3. **페이지가 다 차야 지움.** 엔트리 126개를 다 쓰면 GC가 살아있는 엔트리를 빈 페이지로 옮기고 이 페이지를
   erase — 그럼 이 페이지가 새 빈 페이지가 됨.

플래시를 닳게 하는 건 3단계의 erase뿐.

### 주소 읽는 법

덤프는 파티션만 떼어낸 것이라 그 안의 오프셋은 파티션 기준:

```
플래시 주소 = nvs 파티션 시작 주소 + 오프셋
```

시작 주소는 자기 파티션 테이블에서 확인할 것 — ESP-IDF 기본 레이아웃은 `nvs`를 `0x9000`에 두고
이 문서도 그 값을 쓰지만, CSV를 바꾸면 달라짐.

페이지 내부는 어느 페이지든 동일: 헤더 `+0x00`, 비트맵 `+0x20`, 엔트리는 `+0x40`부터, *n*번 엔트리는
`페이지 시작 + 0x40 + n × 0x20`. 이 덤프에선 ACTIVE 페이지가 page 3(`0xC000`)이라 0번 엔트리가 `0xC040`.

## 5. NVS가 쓰는 페이지

NVS는 페이지 하나만 ACTIVE로 두고 쓰기는 거기로만 감. 애플리케이션이 고를 수 없음 — 페이지는 순서대로
채워지므로, ACTIVE 페이지는 먼저 쓴 쪽(라디오 스택들)이 채우다 만 페이지가 됨. 또 GC가 살아있는
엔트리를 옮길 곳으로 **항상 페이지 하나를 비워 둠.**

한 덤프를 예로 들면:

| 페이지 | 상태 | seq | 내용 |
|---|---|---|---|
| 0 | FULL | 0 | BLE 키, RF 보정값 |
| 1 | FULL | 1 | WiFi 자격증명 (`sta.ssid`, `sta.pswd`) |
| 2 | FULL | 2 | `WIFI_STA_DEF`, `sta.apinfo` |
| **3** | **ACTIVE** | **7** | 네임스페이스 `weather`, 키 `last` |
| 4 | EMPTY | – | 빈 페이지 |

상태와 seq는 **각 페이지 헤더의 첫 8바이트**에 들어 있음. 별도 색인이 없고 페이지마다 자기 번호를
들고 있으며, 아래 `xxd` 루프가 찍는 게 바로 이 값임:

![3단 확대: 페이지 5개 → page 3 내부(헤더 32B · 비트맵 32B · 엔트리) → 그 헤더의 첫 8바이트(0~3번 상태, 4~7번 seq)](nvs-page.png)

위 표의 내용 열은 페이지를 문자열 검색해서 확인한 것. BLE 키는 이 펌웨어가 BLE를 쓰지 않는데도
들어 있음.

**시퀀스 번호는 파티션 전체에 하나뿐인 카운터**로, 페이지가 ACTIVE가 될 때마다 찍히고 재사용되지
않음. 페이지 0–2는 `0, 1, 2`를 달고 계속 FULL이고 ACTIVE 페이지는 `7`. 빠진 `3~6`은 그 뒤 지워지고
재사용된 페이지들의 활성화 번호 — 즉 공백은 '채우고 지우기'가 몇 번 지나갔는지를 알려줄 뿐,
**어느 페이지인지는 말해주지 않음.** 어떤 키가 어느 페이지에 있는지는 기기 수명 동안 바뀌므로,
주소를 재사용하지 말고 매번 새 덤프에서 상태를 다시 읽을 것.

## 6. 갱신 = 추가, 그 비용

**값이 길수록 엔트리를 더 씀** — 저장 1회당 고정 비용이 아님. 이 덤프에선 58바이트가 엔트리 3개,
66바이트가 4개.

**쓰는 주체가 하나가 아님.** WiFi 스택이 접속할 때마다 `WIFI_STA_DEF`를 추가하므로, 웨이크 1회 비용 =
애플리케이션 값의 span + 시스템 스택이 쓰는 엔트리.

같은 덤프의 ACTIVE 페이지를 앞에서부터 갱신 회차로 묶어 보면:

| 엔트리 | 무엇 |
|---|---|
| 0 | 네임스페이스 `weather` 등록 — **평생 1회** |
| **1–3** | **갱신 1회차** : `last` 헤더 1개 + 값 2개 (값 58B) |
| 4 | `WIFI_STA_DEF` — WiFi 스택 |
| **5–7** | **갱신 2회차** : `last` 헤더 1개 + 값 2개 (값 58B) |
| 8, 9 | `WIFI_STA_DEF` ×2 |
| **10–13** | **갱신 3회차** : `last` 헤더 1개 + 값 3개 (값 68B) |
| 14 | `WIFI_STA_DEF` |

**갱신할 때마다 `last`라는 키 문자열까지 새로 씀** — 값만 갈아끼우는 게 아니라 헤더째로 추가되기
때문. 한 번도 다시 쓰이지 않는 건 0번 엔트리의 네임스페이스뿐임.

WiFi 스택이 어떤 웨이크엔 1번, 어떤 웨이크엔 2번(엔트리 8·9) 쓰는 것이 아래 표의 "1~2"의 출처.
옛 값들(`16°C`, `19°C`, `14km/h` …)이 덤프에 그대로 읽히는 것이 추가 방식의 외형.

### 플래시 수명

이 펌웨어, 10분 주기 기준. 값 크기와 주기가 다르면 입력을 바꿔 계산할 것:

| | |
|---|---|
| 웨이크 1회당 소모 엔트리 | 약 5 (값 3~4 + WiFi 1~2) |
| 페이지가 찰 때까지 웨이크 횟수 | 엔트리 126 ÷ 5 ≈ **25회** |
| 하루 웨이크 | 144회 |
| 페이지 erase | 하루 약 5.8회, 연 약 2,100회 |
| NOR 내구성 | 10만 회 |
| **수명** | **약 47년** |

보수적인 값임: 페이지 0–2가 영구히 차 있어 erase는 ACTIVE 페이지와 빈 페이지에만 일어나는데, 위 표는
그 둘을 한 페이지처럼 계산함. 실제로 번갈아 쓰이면 대략 2배.

**테스트한다고 웨이크 주기를 줄이면 마모도 그만큼 비례해서 늘어남** — 이 펌웨어에선
`src/weather/main.cpp`의 `SLEEP_MINUTES`. 10초 주기 = 60배 마모 → 약 47년이 **약 9개월**로 줄어듦.
테스트 끝나면 되돌릴 것.

## 7. WiFi 자격증명이 그대로 들어있음

**WiFi 스택은 접속 자격증명을 NVS에 평문으로 저장함** — SSID, PSK(`sta.pswd`), 직전 IP
(`WIFI_STA_DEF`). 스캔 없이 재접속하기 위한 것이고, 펌웨어가 그렇게 하는 게 아니라 ESP32의 동작임.
이 덤프에선 page 1에 있었음.

따라서 `secrets.h`를 git에서 빼도 비밀번호는 보호되지 않음 — 실제 기기에서 뜬 `nvs.bin`을 공유하지
말 것. 막으려면 ESP-IDF의 Flash Encryption을 써야 하고, eFuse에 구운 키로 플래시 내용을 암호화하는
방식임 (칩에 되돌릴 수 없는 변경이고, Arduino 빌드가 알아서 켜주지 않음).

## 재현하는 법

```bash
# nvs 파티션 덤프 — 오프셋·크기는 자기 파티션 테이블 값으로
# (0x9000/0x5000는 기본 레이아웃, chip·port는 이 보드 기준)
python $(find ~/.platformio/packages/tool-esptoolpy -name esptool.py) \
  --chip esp32c3 --port /dev/cu.usbmodem11401 \
  read_flash 0x9000 0x5000 nvs.bin

# 페이지 상태와 시퀀스 번호
for i in 0 1 2 3 4; do xxd -s $((i*4096)) -l 8 -g 4 nvs.bin; done

# 키 찾기 (오프셋은 파티션 기준)
grep -abo "weather" nvs.bin
grep -abo "last"    nvs.bin

# ACTIVE 페이지의 원본 엔트리 (여기선 page 3이라 0x3040)
xxd -s 0x3040 -l 128 nvs.bin
```

NVS는 **메모리 매핑이 안 됨.** 플래시 MMU가 CPU에 노출하는 건 앱 파티션뿐 — ESP32-C3에선 코드가
`0x42000000`(IROM), 상수가 `0x3C000000`(DROM)이고 칩마다 다름. `0x9000`은 CPU가 볼 수 있는 주소가
아니라 플래시 오프셋이라 GDB로는 NVS에 접근할 수 없음. 값의 위치를 보려면 덤프가 유일한 방법.

`pio run -t erase`는 이 파티션을 지움.
